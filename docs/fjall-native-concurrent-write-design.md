# Fjall 原生并发写入封装设计

日期为 2026-11-24，实施基线为 `fbd72619`，实施和性能验收状态见验收表。

## 目标

- 同一来源生成目录至少有 4 个应用线程同时执行 Fjall 原生写入，默认使用 8 个应用写入线程。
- 在当前 16 个逻辑处理器的 Windows 主机上记录真实批量写入阶段 CPU，超过 40% 为理想性能目标。
- Catalog、Artifact、Timeline 的正文、索引、计数、revision、发布回执保持一致，取消和失败保留当前已发布结果。
- 原始证据保持只读，来源查询句柄在类型层仅提供读取方法。
- 大样本过程遵守现有 2,048 MiB 进程工作集目标，单次真实样本测试最长 15 分钟。
- 使用现有 Fjall、Rayon、crossbeam-channel、Serde 和资源预算设施，删除单写入者封装及其旧调用链。

## 已核对的实现事实

| 位置 | 当前行为 | 设计影响 |
|---|---|---|
| `persistence-fjall/src/database.rs` | `SourceDatabase` 使用乐观事务，并行写入持有共享生命周期许可 | 事务准备支持并发，封存取得独占阶段许可 |
| Fjall `tx/single_writer/mod.rs` | 写事务从创建到结束一直持有 `single_writer_lock` | 增加调用线程数不能提高事务准备并行度 |
| Fjall `batch/mod.rs` | 日志锁覆盖日志编码、持久化和本批次内存表更新 | 原生 batch 支持多线程调用，但提交存在较长串行临界区 |
| Fjall `tx/optimistic` | 支持并发事务、读取集合跟踪和冲突检测 | 适合需要读取后修改的操作 |
| Fjall `ingestion.rs` | `write` 写入原生表构建器，`finish` 获取日志锁协调登记 | 表生成与压缩能够在多个线程执行，完成登记经过原生协调 |
| `lsm-tree/src/tree/ingest.rs` | 严格递增键、直接生成 SST，完成时处理同步和版本登记 | 大批量写入采用原生有序 ingestion |
| `timeline_count.rs`、`record_metrics.rs` | 每个批次更新共享计数和 revision | 大批量写入期间需要使用独立汇总记录 |
| `source-kernel/src/resource_budget.rs` | 默认 CPU 预算最多 6，分析默认 2 个线程 | 新写入线程池需要独立申请资源，并在目标主机获准 8 个线程 |
| `concurrent_analysis_outputs.rs` | 启动 4 个线程并核验最终内容 | 当前断言覆盖结果正确性，原生写入重叠需要新增观测 |

至少 4 个线程同时执行原生写入作为通过条件，CPU 使用率作为性能观测。16 个逻辑处理器上的 40% 相当于约 6.4 个处理器核心，默认 8 个应用写入线程配合 4 个 Fjall 后台工作线程。CPU 统计包含当前进程的原生后台工作，日志同时记录应用工作线程数。

## 数据库和句柄边界

`SourceDatabase` 统一持有 `fjall::OptimisticTxDatabase`，通过其 `inner()` 使用同一个底层 `Database`。同一路径仅有一个共享数据库实例，所有工作线程克隆原生句柄。

| 类型 | 使用位置 | 能力 |
|---|---|---|
| `SourceReadHandle` | 浏览、预览、搜索、摘要、报告、证据挂载 | 创建短期读取快照、分页和点读取 |
| `SourceWriteSession` | 导入、重分析、重建 | 绑定来源、attempt 和目标生成目录，管理工作线程与发布状态 |
| `SourceWorkerWriter` | 每个写入线程 | 持有独立批次、局部计数和原生 ingestion |
| `TransactionReadView` | 读取后修改操作 | 所有点读取和范围读取进入同一原生乐观事务的读取集合 |
| `PreparedGeneration` | 发布协调 | 所有工作线程结束、指标完成、持久化完成后的发布凭证 |

读取接口不导出底层可写数据库、keyspace 和原生批次句柄。写入会话由导入或分析服务显式创建，查询服务只取得 `SourceReadHandle`。

写入会话状态依次为 `Writing`、`Draining`、`Finalizing`、`Prepared`、`Published`。任何写入错误进入 `Failed`，取消进入 `Cancelled`。状态变化使用短期同步保护。工作线程取得并行活动许可后执行原生写入，许可存活期间不持有应用级独占互斥锁。

`Draining` 关闭输入并等待已经接收的工作结束。发布协调在活动写入数为零后取得独占阶段许可。`Prepared` 由受验证的所有权转换产生，发布接口消费该凭证。

## 批量构建路径

适用于导入 Catalog、timeline 文件事件、完整重分析输出和来源生成目录复制。

```mermaid
flowchart LR
    A[来源记录顺序读取] --> B[有界分页]
    B --> C[按记录身份分配工作线程]
    C --> D[8 个应用写入线程]
    D --> E[编码正文和索引]
    E --> F[局部有序批次]
    F --> G[Fjall 原生 ingestion.write]
    G --> H[原生 ingestion.finish]
    H --> I[有界计数汇总]
    I --> J[验证与持久化]
    J --> K[发布生成目录]
```

### 工作分配与一致性

1. 使用现有记录身份和稳定键编码，将相同逻辑记录分配给同一个工作线程。线程内部按输入序号处理。同一个记录的替换和删除使用相同归属规则。
2. 在同一替换范围内完成旧记录和旧索引删除，再开放该范围的新记录写入。范围之间可以并发。
3. 每个工作线程在前一批次完成后取得短期目标快照，读取本批次身份已有的正文，复用现有旧索引删除、正文和新索引生成逻辑。相同身份归属同一个线程，因此跨批次重复记录按输入顺序替换。同批次先按身份合并，保留最后一个记录，再计算计数增量。
4. 写入操作按 keyspace 分组，每组排序并消除同批次的重复键，保留输入顺序中最后一个操作。准备结束立即释放检查快照。
5. 每个有序批次创建原生 ingestion。写入键严格递增，删除使用原生 `write_tombstone`。每个线程直接执行 `write` 和 `finish`。
6. 每个批次成功结束后记录独立完成回执。回执包含 attempt、线程、批次序号、记录数量和现有操作摘要。协调者根据回执汇总实际完成数量。
7. 目标生成目录在完整发布前不提供业务查询。正文和索引经过独立 keyspace ingestion 后，在生成目录发布边界一起可见。
8. 所有工作线程完成后核验正文、索引、回执和计数。发布协调执行 `SyncAll`、现有 seal 及来源控制事务，然后切换活动生成目录。

单次 ingestion 的跨 keyspace 写入不提供原子事务，完整生成目录的发布承担整体可见性边界。需要即时可见的读取后修改操作进入下方乐观事务路径。

来源生成目录复制采用有界 keyspace 页和同一并发写入会话。不可变正文校验继续复用现有摘要逻辑。复制完成前不会发布目录。

### 有序批次和队列

| 资源 | 初始执行参数 | 约束 |
|---|---:|---|
| 应用写入线程 | 8 | 可配置 4、8，目标主机必须获准至少 4 |
| Fjall 后台工作线程 | 4 | 用于原生写出与压缩 |
| 单个应用批次编码数据 | 8 MiB | 单条记录超出预算时在入口返回类型化错误 |
| 每个线程待处理批次 | 1 | 接收下一个批次前释放上一批次预算 |
| 每个线程活动批次 | 1 | 不跨批次保留读取快照 |
| 同一线程活动 ingestion | 1 | 按 keyspace 逐个完成 |
| 全部应用输入及编码缓冲 | 256 MiB | 纳入现有进程资源预算 |
| 读取分页 | 现有条数上限和字节上限 | 页交给线程后转移所有权 |

排序使用 Rust 标准库对单个有界批次排序，SST 生成、编码、压缩和合并由 Fjall 原生实现承担。并发进入原生 ingestion 的线程数独立计量。

工作池使用 Rust scoped threads 和现有 crossbeam-channel 有界通道，每个线程只有一个待处理批次。输入按实际容量估计字节，单条记录及编码批次均检查字节上限，工作线程合并小批次后直接进入原生 ingestion。Fjall 的当前写入缓冲、封闭内存表、历史版本和压缩任务另行计量，所有存储资源共同参与进程资源验收。

统一 CPU 预算计入 8 个应用写入线程和 4 个 Fjall 后台线程，当前主机的 16 个逻辑处理器满足该申请。写入会话的准入能力需要取代现有最多 6 个线程的限制。至少 4 个写入线程无法准入时返回类型化资源错误，任务状态明确记录资源不足。

每批次生成的 SST 数量、重叠范围及压缩积压纳入观测。数据文件大小、表数量和压缩等待需要与原生 batch 的单线程基线比较，避免仅凭提交完成时间判定吞吐量。

## 共享计数和 revision

工作线程提交正文、索引和独立批次回执。全部工作线程完成后，Catalog 按正文分页重建总数、文件数和孤立目录标记，Timeline 使用已有计数重建逻辑计算类型及时间桶。Artifact 的独立写入继续在分析发布前重建指标。重建核验数量溢出和负数结果。

计数与 revision 通过乐观事务发布，构建完成标记随后写入。新生成目录在完整发布前保持不可供业务查询，最终验证逐项比较正文计数和索引查询结果。

revision 在一次完整生成目录发布中推进一次。工作线程的中间提交不推进已发布来源的 revision。

## 读取后修改路径

需要在当前数据基础上修改记录和索引的操作使用 `OptimisticTxDatabase::write_tx()`。

- 读取正文、旧索引、共享计数和 revision 时使用同一个 `TransactionReadView`。
- `get`、`contains_key` 和范围读取均使用原生事务读取方法，进入 Fjall 冲突检测。
- 删除 `write_planned` 接受普通 `SourceReadSnapshot` 的形式，防止事务读取集合遗漏。
- 同一事务原子写入正文、旧索引删除、新索引、计数、revision 和操作回执。
- `Conflict` 作为类型化并发冲突返回调用者，该次提交没有可见变化。调用者需要重新获取快照并重新执行完整业务操作。
- I/O 错误立即结束当前会话并保留错误原因，发布协调拒绝该会话。

共享计数密集更新的大批量任务使用构建路径，日常的读取后修改由乐观事务保持原子一致性。

## 快照、只读与发布

目录枚举读取当前已发布生成目录，写入位于不同的目标生成目录。枚举结束立即释放目录读取快照。

旧记录删除快照只覆盖删除过程。插入批次的检查快照只覆盖当前批次。图谱构建在 timeline 发布后创建读取快照，结束后立即释放。

`SourceReadHandle` 的只读能力限制在封装 API 层。Fjall 打开数据库时自身可能执行恢复或后台维护，封装的只读类型不构成操作系统级只读打开声明。原始 E01 和父证据仍由证据读取层以只读方式访问。

现有 `immutable_gate` 由会话生命周期控制和发布独占阶段替代。完整写入期间不持有应用级全局独占锁。不可变正文 epoch 和 seal 检查在写入线程全部结束后执行。

## CPU 与吞吐量测量

Windows 使用同一进程的累计处理器时间差计算 CPU。

`CPU 百分比 = 100 × 进程处理器时间差 / 墙钟时间差 / 逻辑处理器数`

指标从批量写入阶段开始采集，到该阶段所有原生写入及收尾结束为止。每秒采样，报告整段时间加权平均值及每个连续 30 秒窗口。输入读取、编码、排序、原生写入、等待、计数汇总和发布分别计时，完整阶段 CPU 同时报告。

验收保留以下观测。

- 有效正文记录/秒、正文与索引编码字节/秒、完成回执数量。
- 已启动写入线程数、同时处于原生 `ingestion.write` 调用范围的线程峰值、并发原生写入覆盖时间。
- 原生 `write` 与 `finish` 用时，输入队列等待、资源等待、原生背压等待和发布用时。
- 工作集、私有内存、当前写入缓冲、历史版本、活动压缩和队列字节峰值。
- 数据库正文数量、索引数量、分类计数、时间桶、来源归属、revision 和发布回执。

至少 4 个线程同时执行原生写入作为并发通过条件。CPU 超过 40% 为理想性能目标，与有效吞吐量共同报告。CPU 工作来自实际来源读取、正文编码、索引生成、排序、压缩或存储。
